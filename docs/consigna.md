# Examen Final — Programación Multimedial IV

## Portfolio web personal e interactivo

Este examen final propone que desarrolles un portfolio web que te presente como persona, estudiante y profesional del campo multimedial. El resultado debe comunicar quién sos, qué te interesa, qué sabés hacer y cómo pensás cuando diseñás y programás una experiencia.

No se evalúa solamente una página visualmente atractiva. Se evalúa una propuesta con identidad, decisiones justificadas, implementación sólida, interacción significativa y evidencia del proceso.

## Propósito

El portfolio debe funcionar como una pieza digital que puedas compartir y defender. Tiene que mostrar una mirada propia sobre tu recorrido, tus intereses y tus capacidades, y al mismo tiempo demostrar los aprendizajes técnicos de la materia.

La consigna es deliberadamente abierta: podés definir el tono, el relato, la estructura, los contenidos y el lenguaje visual que mejor representen tu propuesta.

## Consigna

Diseñá y desarrollá un portfolio web personal e interactivo.

Tu portfolio puede presentarse como un sitio editorial, una experiencia narrativa, un archivo visual, una interfaz experimental, un recorrido audiovisual, una herramienta, una escena interactiva o cualquier otra forma que tenga sentido para vos. La libertad estética y tecnológica es parte de la consigna.

La única tecnología obligatoria es AstroJS. Fuera de ese requisito, podés elegir libremente tus lenguajes, librerías, frameworks complementarios, herramientas de estilos, fuentes, recursos multimedia y estrategia de despliegue.

**Importante:** Tailwind CSS no es obligatorio. Podés usarlo, reemplazarlo o no utilizar ninguna librería de estilos.

## Qué debe comunicar

La experiencia debe permitir comprender, de manera clara aunque no necesariamente convencional:

- quién sos y qué lugar ocupás en el campo multimedial;
- qué intereses, preguntas o temas orientan tu trabajo;
- qué proyectos, habilidades o aprendizajes querés destacar;
- qué decisiones conceptuales y formales distinguen tu propuesta;
- cómo puede una persona recorrer, interpretar y recordar la experiencia.

No hace falta convertir el portfolio en un currículum tradicional. Sí hace falta que la forma elegida ayude a comunicar una identidad reconocible y una intención concreta.

## Requisitos técnicos

El proyecto debe cumplir con todos los siguientes requisitos:

- **AstroJS:** el proyecto debe estar desarrollado con AstroJS y poder ejecutarse a partir de las instrucciones del README.
- **Diseño responsive:** la experiencia debe ser usable y legible en pantallas grandes y pequeñas. No alcanza con que el contenido simplemente se reduzca.
- **Tres componentes propios relevantes como mínimo:** deben resolver partes significativas de la experiencia y estar integrados con una responsabilidad clara. No cuentan como componentes relevantes únicamente elementos decorativos o bloques repetidos sin lógica propia.
- **Navegación:** debe existir una forma clara de recorrer las secciones, vistas o estados del portfolio, aunque la navegación no sea convencional.
- **Interacción significativa:** al menos una interacción debe modificar la experiencia, el contenido, el estado o la lectura de manera intencional. Una animación automática sin efecto en la experiencia no alcanza por sí sola.
- **API externa o fuente dinámica:** el portfolio debe consumir una API externa o trabajar con una fuente dinámica de datos. Documentá qué fuente utilizás, qué información obtenés y cómo manejás sus límites o errores.
- **Estados pertinentes:** contemplá los estados que correspondan a tu propuesta: carga, contenido disponible, error, vacío, selección, navegación, reproducción, respuesta a una acción u otros. No es necesario agregar estados artificiales; sí resolver los que la experiencia realmente necesita.
- **Deploy:** el portfolio debe estar publicado en una URL accesible durante la evaluación.
- **Repositorio:** el código debe estar disponible en un repositorio accesible, con historial suficiente para reconocer el desarrollo del proyecto.

La elección tecnológica tiene que estar al servicio de la propuesta. Usar más herramientas no implica necesariamente una mejor solución.

## Entregables

Presentá los siguientes elementos:

1. **URL del portfolio publicado.** Verificá que funcione sin depender de tu máquina local.
2. **URL del repositorio.** El repositorio debe incluir el código fuente y los recursos necesarios para comprender el proyecto.
3. **README completo**, que incluya como mínimo:
   - descripción breve de la propuesta y del público al que se dirige;
   - instrucciones para instalar dependencias, ejecutar y construir el proyecto;
   - tecnologías y decisiones principales;
   - explicación de los componentes propios relevantes;
   - fuente dinámica o API utilizada, incluyendo comportamiento ante error o ausencia de datos;
   - criterios de responsive y accesibilidad considerados;
   - limitaciones conocidas y posibles líneas de mejora;
   - créditos y licencias de recursos de terceros, cuando corresponda.
4. **Evidencia de proceso**, integrada en el repositorio o enlazada desde el README. Puede incluir exploraciones, wireframes, prototipos, pruebas, iteraciones, decisiones descartadas, registros de problemas y soluciones, capturas o bitácora.

## Evidencia de proceso

La evidencia debe permitir reconstruir cómo llegaste al resultado, no solamente mostrar la versión final. Registrá especialmente:

- qué problema de comunicación o presentación quisiste resolver;
- qué alternativas exploraste y por qué elegiste una;
- cómo evolucionaron la estructura, la identidad visual y las interacciones;
- qué pruebas realizaste en distintos tamaños de pantalla;
- qué dificultades técnicas encontraste y cómo las resolviste;
- qué parte del resultado todavía reconocés como pendiente o mejorable.

La evidencia no necesita ser extensa ni estar presentada como un informe académico. Tiene que ser concreta, honesta y suficiente para mostrar decisiones y aprendizaje.

## Defensa individual

La evaluación incluye una defensa individual del proyecto. Durante la defensa deberás:

- explicar la intención y el recorrido de la experiencia;
- justificar decisiones de diseño, arquitectura y tecnología;
- mostrar el funcionamiento del portfolio publicado;
- responder preguntas sobre el código, los componentes, los datos y los estados;
- realizar una modificación menor en vivo, indicada durante la instancia de evaluación.

La modificación en vivo busca comprobar que comprendés tu propio proyecto y que podés intervenirlo con criterio. No se espera incorporar una funcionalidad grande, sino resolver un cambio acotado sobre una parte existente.

## Uso de inteligencia artificial

Podés utilizar herramientas de inteligencia artificial como apoyo durante el proceso, de manera responsable. La responsabilidad sobre el resultado, el código y las decisiones es tuya.

Si utilizás IA, registrá en el README o en la evidencia de proceso:

- para qué tareas la utilizaste;
- qué partes revisaste, adaptaste o descartaste;
- qué problemas, errores o límites detectaste;
- qué decisiones fueron tomadas por vos.

No presentes como propio un resultado que no comprendés. Durante la defensa deberás poder explicar y modificar el código que entregues. La IA puede asistir el proceso, pero no reemplaza la autoría, la verificación ni la capacidad de argumentar.

## Criterios de evaluación

| Criterio                    | Porcentaje | Se observa especialmente                                                                          |
| --------------------------- | ---------- | ------------------------------------------------------------------------------------------------- |
| Identidad y concepto        | 20%        | Claridad de la propuesta, mirada personal, coherencia entre lo que comunica y cómo lo comunica.   |
| Creatividad y experiencia   | 20%        | Originalidad, capacidad de exploración, calidad del recorrido y sentido de las decisiones interactivas. |
| Arquitectura, componentes y código | 20% | Uso de AstroJS, organización del proyecto, calidad de los componentes propios, legibilidad y criterio técnico. |
| Integración e interacción   | 15%        | Integración de la API o fuente dinámica, interacción significativa, manejo de estados y respuesta ante situaciones pertinentes. |
| Responsive y accesibilidad  | 10%        | Adaptación a distintos tamaños, legibilidad, navegación, contraste, foco, textos alternativos y otras decisiones de accesibilidad pertinentes. |
| Proceso y documentación     | 5%         | README, instrucciones reproducibles, créditos, evidencia de proceso y registro de decisiones.     |
| Defensa                     | 10%        | Comprensión del proyecto, capacidad de argumentar, responder preguntas y realizar una modificación menor en vivo. |
| **Total**                   | **100%**   |                                                                                                   |

## Checklist antes de entregar

- El proyecto utiliza AstroJS.
- La URL publicada funciona y fue probada en más de un tamaño de pantalla.
- La propuesta es abierta, pero no es indefinida: elegí un alcance que puedas terminar, probar, documentar y defender con solvencia.
- Hay al menos tres componentes propios relevantes.
- La navegación y la interacción principal se entienden y funcionan.
- La API o fuente dinámica está integrada y documentada.
- Los estados pertinentes están resueltos.
- El repositorio es accesible y contiene el código fuente.
- El README permite instalar, ejecutar y comprender el proyecto.
- La evidencia muestra decisiones y evolución, no solamente el resultado final.
- Podés explicar y modificar tu propio código durante la defensa.
